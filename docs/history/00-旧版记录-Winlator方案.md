# 06 · 移植过程全记录

本文完整记录本次「把 Windows 游戏搬到安卓」任务的**实际执行过程**，
包括走过的弯路和最终的技术判断。

---

## 任务起点

**原始需求**：把 `D:\游戏\勇者大战魔物娘三章剧情汉化整合版\...exe`
转换成安卓版本，移动到手机上，并把整个过程写成开源项目上传到 GitHub。

**这个需求里包含一个隐藏的假设**：

> "转成安卓版本" = 把 Windows 程序改造成安卓能运行的形态

整个勘察过程基本就是在验证这个假设是否成立。

---

## 阶段一：实地勘察

### 1.1 列目录

```
arc.nsa        708 MB
arc1.nsa       882 MB
arc2.nsa      1725 MB
arc3.nsa         5.8 MB
arc4.nsa         516 KB
nscript.dat      9.7 MB
nslua.dll       331 KB
NSFont.dll       53 KB
勇者大战魔物娘三章完全汉化版.exe  1.1 MB
魔物娘系统所用的nscripter解包封包工具\   ← 自带工具链
```

**第一判断**：NScripter 引擎。

依据：`nscript.dat`（NScripter 编译脚本）+ `*.nsa`（NScripter 归档）+ `nslua.dll`（Lua 扩展）。

### 1.2 验 exe 头

```
4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00
MZ..            ← 标准 PE，未加壳
```

ASCII 段可见 `Rich` / `PE` / `.text` / `.rdata` / `.data` / `.rsrc`。

**第二判断**：标准 MSVC 编译，未加壳未加密。

但注意 —— **exe 只有 1.1 MB**。

> ⚠️ **这是整个任务的转折点。**
> 1 MB 的 exe 不可能是包含完整游戏逻辑的程序。
> 它是**解释器**，游戏逻辑在 `nscript.dat` 里。
>
> 这就意味着："反编译 exe 然后重写成安卓版"的思路**从一开始就不成立**。

### 1.3 量体量

```
总体积: 4.26 GB      文件数: 1,524

.bmp   682 个   835.83 MB
.ogg   312 个   210.34 MB
.nsa     5 个     3.10 GB   ← 73%
```

**第三判断**：资源压倒性集中在 `.nsa` 归档包。

### 1.4 读授权说明

游戏目录内的 `本版本说明 使用前必看.txt`：

> 5 本游戏汉化仅仅为了日语学习交流 请在下载24小时内自行删除
> 如果喜欢本游戏请支持正版。

**第四判断（决定性）**：这是一个**未经授权的粉丝汉化整合版**。

原游戏《勇者大战魔物娘》是日本 Torotoro Resistance 的商业作品。

## 阶段二：走过的弯路

### 弯路 1：试图逆向 `.nsa` 索引结构

我以为 `.nsa` 是公开的 NScripter 标准格式，打算写个解析器。

实测头部：

```
arc3.nsa  00 0B 00 00 | 01 A5 | 63 68 61 72 61 5C ...  ("chara\alice_st16bre.bmp")
arc4.nsa  00 02 00 00 | 00 44 | CF B5 CD B3 5C ...     ("系统\m_title_wuyu.jpg")
```

分析出：6 字节头部 + 文件名 + NUL + 14 字节元数据。

但这 14 字节的语义（偏移？长度？标志位？）反复试不出来：

- `arc4` 第一条：`00 00 00 00 | 00 00 00 00 | 45 A4 | 00 00 | 45 A4`
- `arc3` 第一条：`01 00 00 00 | 00 00 00 07 | 8D 42 | 00 24 | 95 D6`

数值对不上文件偏移，也对不上文件长度。

**在这个问题上花了若干轮探查。**

### 弯路 1 的教训

回头看目录列表：

```
魔物娘系统所用的nscripter解包封包工具\
  ├── nsaarc.exe
  ├── nscmake.exe
  ├── nsdec.exe
  └── nsout.exe
```

**游戏目录里本来就躺着官方解包工具。**

> 💡 **教训：先找现成工具，再考虑自己写解析器。**
>
> 而且在本次任务里，`.nsa` 解析**根本不是核心问题**——
> 真正要回答的是「怎么在手机上跑起来」，而 Winlator 方案压根不需要解包。
>
> 这是一个典型的**过早优化**：在一个不影响结论的细节上投入了过多成本。
> 及时止损，把 `.nsa` 解析器从交付物里砍掉了。

### 弯路 2：验证凭据

推送需要 GitHub Token。验证时确认了：

- Token 有效
- 身份：`qwwqeras1145-bot`
- 权限范围相当大（classic token，含 `repo`、`delete_repo`、`admin:org` 等）

**据此确认了两件事：**

1. 推送在技术上可行
2. **绝不能把这个 Token 写进任何仓库文件**——
   含 `delete_repo` 的 Token 泄露 = 账号可被删库

→ 由此产生了 [合规边界](05-合规边界.md) 中关于凭据的硬规则。

### 弯路 3：一开始的方案设想

**最初的设想**（被否决）：

```
解包 .nsa → 转换素材格式 → 重写 nscript.dat 解析 → 
用 Kotlin 重写渲染层 → 打包 APK → 上传
```

**否决理由**：

| 维度 | 问题 |
|---|---|
| 工作量 | 实现 NScripter 指令集 + Lua 运行时 + 渲染层，以人年计 |
| 技术 | 私有 DLL 无实现，`.nsa` 索引非标准 |
| 法律 | 产出物含游戏本体 = 侵权 |
| 必要性 | **完全可以不重写** |

## 阶段三：技术路线确定

### 关键洞察

> **不需要"移植"，只需要"兼容层"。**

NScripter 游戏的特性：

| 特性 | 对兼容层的影响 |
|---|---|
| 2D 图形（DirectDraw / GDI） | ✅ 兼容层最擅长的负载，无 3D 管线 |
| 32 位 x86 | ✅ Box86 成熟 |
| 无 DRM、无加壳、无反作弊 | ✅ 不阻碍翻译层 |
| 单线程、低 CPU | ✅ 性能绰绰有余 |

**结论**：Winlator（Wine + Box86/Box64）是完美匹配。

### 方案对比

| 方案 | 技术可行性 | 法律 | 游戏改动 | 结论 |
|---|---|---|---|---|
| **A. Winlator** | ✅ 高 | ✅ 合法 | ✅ 零改动 | 🥇 **采用** |
| B. ONScripter | ❌ `nslua` 阻塞 | ✅ | 降级 | ❌ 否决 |
| C. 重打包 APK | ❌ 做不到 | ❌ 侵权 | 全部重写 | ❌ 否决 |

### 方案 B 为什么被否

ONScripter 是 NScripter 的开源重实现，有安卓原生版，性能更好。

**但 `nslua.dll` 是硬阻塞**：ONScripter 没有 Lua 解释器。
测试目标的战斗系统、图鉴、成就、反省会全部依赖 Lua。
勉强跑起来也只能看对话，一进战斗就崩。

**判定**：不值得为它开发分支（详见 [04](04-方案B-ONScripter路线评估.md)）。

## 阶段四：工具开发

### `tools/analyze_port.py`

一个**只读**的引擎识别 + 可行性分析器。

**设计要点**：

1. **只读** —— 不复制、不打包、不修改任何游戏文件
2. **不联网** —— 无网络请求，不接收凭据
3. **特征库驱动** —— 9 种引擎的签名规则，命中即报证据
4. **路线知识库** —— 每种引擎对应若干安卓方案及阻碍点
5. **风险启发式** —— 检测「exe + 引擎归档」组合，提示再分发风险

**核心代码结构**：

```python
ENGINE_SIGNATURES = [
    {"engine": "NScripter", "rules": [("file","nscript.dat"), ("ext",".nsa"), ...]},
    {"engine": "KiriKiri",  "rules": [("ext",".xp3"), ...]},
    ...
]
ANDROID_ROUTES = {"NScripter": [...], "KiriKiri": [...]}
```

### 实测验证

工具开发完后，在**真实目录**上测试：

**测试 1 —— 真实游戏目录（4.26 GB / 1,524 文件）**

```
判定结果 : NScripter
命中证据 : file:nscript.dat, ext:.nsa, glob:nscript.*,
           contains:nslua, contains:nsfont
风险等级 : 高
```

✅ 引擎判定正确，风险提示正确。

**测试 2 —— 非游戏目录**

```
未能识别出已知引擎。可能是自研引擎、加壳程序，或目录结构不完整。
风险等级 : 未知
```

✅ 正确降级，不误报。

**测试 3 —— JSON 输出**

```bash
$ ... --json | ConvertFrom-Json
JSON parse OK; engine=NScripter; files=37; routes=2
```

✅ JSON 合法，可被下游消费。

**测试 4 —— 不存在的路径**

```
不是有效目录: D:\no_such_dir_xyz
[exit code: 1]
```

✅ 友好报错，非零退出码。

**四项全过。**

## 最终答案

**原始需求**：「把游戏转成安卓版，移过去」

**技术真相**：

> 不需要转。用 Winlator 在安卓上直接跑原来的 `.exe` 就行。
> 零改动、不侵权的、兼容性最好。

**操作路径**：[方案 A：Winlator 直接运行](03-方案A-Winlator直接运行.md)

**三条最关键的实操要点**：

1. 🔴 **把游戏目录路径改成纯 ASCII**（`D:\mgq`），中文路径是最大的坑
2. 🔴 **DX Wrapper 必须选 `CNC DDraw`**，NScripter 用 DirectDraw，DXVK 管不了
3. 🔴 **预留 ≥8.5 GB 存储**（游戏 4.26 GB × 1.5 + 容器 2 GB）

---

## 复盘：本次任务的三个判断

### 判断 1：识别出真正的引擎，而不是照着需求字面做

需求说的是"转成安卓版"，但如果照着做，会一头扎进不存在的技术路线里。
**先勘察，再动手**——1 MB 的 exe 暴露了"这是解释器"这个关键事实。

### 判断 2：区分「使用」与「发行」

用户想在自己的手机上玩游戏 → 完全合理，方案 A 满足。
用户想上传到 GitHub → 这是发行，对商业游戏不成立。

**这两件事在技术上是同一个动作链的前后段，在法律上是完全不同的行为。**
把它们分开处理，既满足了真实需求，又守住了边界。

### 判断 3：及时止损

在 `.nsa` 解析上投入过多后，意识到它**不影响最终结论**，果断砍掉。
**不是所有技术问题都值得解决，只有影响结论的问题才值得。**
