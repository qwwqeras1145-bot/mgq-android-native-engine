# 移植过程全记录

本文按**实际发生的时间顺序**记录这次「把 NScripter 游戏做成原生安卓版」的完整过程，
包括每一步的判断依据、走过的弯路、以及被实测推翻的结论。

> 记录原则：**只写实际验证过的结果**。凡没跑通、没测过的，明确标注为未验证。
> 旧版记录（当时结论是「必须用 Winlator」）保留在 [history/](history/)，供对照。

---

## 0. 任务起点

原始需求：

> 把 `D:\游戏\勇者大战魔物娘三章剧情汉化整合版\勇者大战魔物娘三章完全汉化版.exe`
> 转换成安卓版本，移到手机，并在 D:\开源项目 新建项目记录全部移植过程，上传 GitHub。

### 0.1 核查发现的既有资产

这台电脑上**已经存在**一个相关项目：

```
D:\开源项目\06-游戏移植\NScripter安卓运行方案\
```

内含 6 篇文档、1 个分析工具、Winlator 传输脚本，**已推送到 GitHub**
（`qwwqeras1145-bot/nscripter-android-guide`，4 次提交）。

它当时的结论是：**「不要移植，用 Winlator 兼容层」**，理由是
`nslua.dll` 提供了 Lua 扩展，开源引擎无法实现，所以只能靠 Wine 跑原版 exe。

**这个结论在本次被实测推翻**（见 §2.2），这是整个任务的转折点。

### 1.1 列目录

```

魔物娘系统所用的nscripter解包封包工具\   ← 自带工具链
```

**判断：NScripter 引擎。**
依据：`nscript.dat`（编译脚本）+ `*.nsa`（归档）+ `nslua.dll`（Lua 扩展）。

### 1.2 验 exe 头

```
4D 5A 90 00 ...   → MZ，标准 PE，未加壳
```

exe 只有 1.1 MB。

> ⚠️ **关键判断**：1 MB 的 exe 不可能是完整游戏逻辑。
> 它是**解释器**，逻辑在 `nscript.dat` 里。
> ⇒「反编译 exe 重写成安卓版」的思路从一开始就不成立。

### 1.3 量体量

```
总体积 4.26 GB / 1,524 文件（外层）
.bmp  682 个  835 MB
.ogg  312 个  210 MB
.nsa    5 个  3.10 GB   ← 73%
```

### 1.4 解出脚本（关键一步）

用游戏自带的 `nsdec.exe` 解包：

```
nsdec.exe nscript.dat    →  result.txt (10,119,146 字节)
```

**踩坑**：第一次用管道 `| Select-Object -First 5` 读它的输出，导致进程被提前掐断，
`result.txt` 为 0 字节。改为 `Start-Process -RedirectStandardOutput` 后正常。

> 💡 **教训**：`nsdec.exe` 会向 stdout 吐 222 MB 进度日志，绝不能用管道限制条数去读它。

## 2. 阶段二：推翻「必须用 Lua」的旧结论

### 2.1 脚本统计（真实数据）

```
行数        : 382,325
标签        : 9,771
numalias    : 1,200
stralias    : 0
defsub 宏   : 18
不同指令    : 163
编码        : GBK（cp936），零非法字节
```

### 2.2 决定性发现：Lua 引用 = 0

对解密后的全文和**原始字节流**做两次独立扫描，搜索
`lua` / `nslua` / `luac` / `.lua`：**结果全部为 0。**

`nslua.dll` 只是引擎发行包里附带的一个可选扩展，**游戏逻辑根本没有使用它**。
战斗系统是用 NScripter 自己的 `defsub` 宏实现的：

```
defsub name / vspl / cspl / damage / damage_nobr / skillname /
       sean_change / count / screen_clear / screen_clear2 /
       screen_vanish / screen_appear / hseanwave / hseanvoice /
       skillcount1 / skillcount2 / skillcount3
```

> ✅ **结论**：旧项目「因为 nslua 所以只能 Winlator」的判断**不成立**。
> 原生实现不需要 Lua 运行时，技术路线打通。
>
> **这一条把「只能跑模拟器」变成了「可以写原生引擎」。**

## 3. 阶段三：破解两个二进制格式

原生实现必须自己解析这两个格式，不能依赖 Windows 工具。

### 3.1 `nscript.dat` 编码：XOR 0x84

用**已知明文攻击**（已有 `nsdec.exe` 产出的明文）做差分分析：

```
raw[i] = dat[i] XOR 0x84
```

等长、无状态、位置无关、常数密钥、无密钥流、**没有任何压缩**。

那为什么明文比密文大 382,324 字节？

> 因为原厂 `NSDEC.EXE` 用 CRT 文本模式写输出文件，把每个 `LF` 展开成了 `CRLF`。
> **这是工具的副作用，不是格式的一部分。**
> 引擎真正读到的是纯 LF 的 `nscript.dat ^ 0x84`。

**闭环验证**：

| | sha256 |
|---|---|
| `result.txt`（原厂工具产出） | `43ea4b72dd19fafa52afc5022f8a238a60da7d9ab1d930f0d3219ac9d2fcfb39` |
| 我方独立实现解码 | `43ea4b72dd19fafa52afc5022f8a238a60da7d9ab1d930f0d3219ac9d2fcfb39` |

逐字节完全相同。另外 `encode(decode(x)) == x` 也成立（严格互逆）。

### 3.2 `.nsa` 归档：**这里走了最长的弯路**

这是整个任务里耗时最多的部分，值得完整记录失败的路径。

#### 失败尝试 1：以为索引是「文件名 + 偏移 + 长度」

手工读 `arc4.nsa` 头，推定 `00 02` = 条目数 2、`00 44` = 索引长度 68。
看起来完美：68 + 17828 + 499053 = 516949 = 文件总长
（17828 和 499053 是 `system\` 目录里两个文件的实测大小）。

**但这个模型在 `arc3.nsa` 上立刻崩了。**

#### 失败尝试 2：字节序反复读错

在 PowerShell 里打印原始字节时，我把十六进制和十进制混淆了多次，
导致同一个字段一会儿是 512、一会儿是 2816、一会儿是 375。
每次「修正」后又与另一个归档冲突。

> 💡 **教训**：**只要在字节层面反复出错，就不要继续手工推演，
> 应该写一个脚本把原始十进制值一次性打全。**
> 我最后这样做时才看清：`bytes[0..5] = [0, 2, 0, 0, 0, 68]`。

#### 失败尝试 3：以为所有归档布局相同

实际探测到的事实：

| 归档 | 文件名槽宽 | 记录跨距 | 探测到的载荷对象数 |
|---|---|---|---|
| `arc4.nsa` | 24 字节 | 33 字节 | 14 |
| `arc3.nsa` | 28 字节 | 37 字节 | 46 |

**不同打包器版本产生的归档布局不同**，而且 `byte[1]` 这个看起来像条目数的字段
对 `arc4.nsa` 来说是 2，但实际有 14 个载荷对象。

#### 最终采用方案：不解析索引，改用签名扫描

关键洞察：

> **载荷是未压缩、连续存放的，而且每个资源都有明确的文件头魔数。**

所以不再试图重建索引格式，而是：

1. 流式分块扫描归档，用魔数（BMP `BM` / JPEG `FF D8 FF` / PNG / OggS / RIFF / ID3）定位载荷对象；
2. 相邻对象之间的字节区间就是该资源的数据（最后一个是到文件尾）；
3. 索引区只用来**尽力恢复文件名**，恢复不到就用序号命名。

**这是一个显式的工程取舍**，已写进代码注释：

- 对**数据**是精确的（区间由签名和文件长度界定）
- 对**文件名**是尽力而为的（Kotlin 侧有 `nameConfidence()` 明示恢复率）

**实测结果**：

```
arc4.nsa : payload=14  首个对象 @68（FF D8 FF E1，JPEG Exif）  names=partial (2 of 14)
arc3.nsa : payload=46  首个对象 @279637（BM）                  names=partial (11 of 46)
```

对象定位与魔数、文件长度完全自洽；文件名对两个归档都能恢复出正确路径
（`chara/alice_st16bre.bmp` 等），只是数量少于对象数（部分资源无扩展名可识别）。

#### 性能修正（重要）

第一版实现用 `file.readBytes()` 整文件读入 + 逐字节循环判断魔数。

> ❌ 这在手机上**不可接受**：`arc2.nsa` 有 1.7 GB，
> 既会耗尽内存，逐字节解释执行也会慢到不可用。

改为：只读 64 字节文件头 → 4 MB 分块流式扫描 → 块内用数组搜索而非逐字节循环 →
处理跨块边界的签名（保留 3 字节 carry）。

## 4. 阶段四：引擎核心实现

### 4.1 架构决策：核心与平台分离

**最关键的一个设计决定**：

```
core/    纯 Kotlin / JVM，零 Android 依赖  ← 可以在电脑上直接测
android/ 薄壳：Canvas 渲染 / MediaPlayer / SAF 存储
```

理由：如果引擎核心依赖 Android，那么每次验证都要装 APK、连手机，
380k 行脚本的回归测试根本没法做。分离之后，我可以在电脑上直接对
**真游戏数据**跑解析器和 VM，并产出可复现的测试报告。

**这个决定直接决定了本次能有多少结论是「测过的」而非「看起来对」。**

### 4.2 解析器的 bug 收敛过程

解析器是真刀真枪在 382k 行真实脚本上跑出来的，问题数变化如下：

| 迭代 | 问题数 | 修复内容 |
|---|---|---|
| 1 | 48,950 | 初始版本 |
| 2 | 48,950 | 加 `?name[n]` 数组指令（未生效） |
| 3 | 48,950 | 修 `parseCondition` 异常吞掉候选前缀 |
| 4 | 8,663 | 修 `splitIf`：**条件与命令之间是空格而非冒号**（48,947 处） |
| 5 | 162 | 处理 `if COND CMD:CMD` 混合形式 |
| 6 | 83 | 制表符分隔的多 token 前缀 |
| 7 | 60 | 间接变量 `%%skill_num` 双重解引用 |
| 8 | **6** | 剩余均为脚本原文笔误 |

#### 修掉的具体 bug（都有真实数据佐证）

1. **`if` 的两种形式被混淆**
   全脚本 `if` 共 48,949 处，其中**块形式只有 2 处**，其余全是
   `if <条件> <命令>` 行内形式。我一开始按「冒号分界」处理，导致 4.8 万行解析失败。

   > 📌 顺带推翻了另一份侦察报告的结论：它声称有 70 处「块头 if」。
   > 实测真正的「`if` 单独成句」**只有 1 处**（L92）。

2. **`*label:命令` 内联形式**
   脚本里有 `*wind_guard_kakuritu:if %wind_guard_on=0 skip 2`。
   我最初把冒号后内容并进了标签名，造成 58 个「假断链」。

3. **`if %3083>0mov %list_num3,1`**
   原作者漏了空格。用「命令 token 边界」正则（左侧必须是数字/`)`/`]`）切分，
   同时保证不会误伤 `%movecount` 这种变量名。

4. **`%%name` 间接变量**
   技能统计宏的核心：`getparam` 拿到的是**变量编号**，
   之后用 `%%skill_num` 取该编号的变量——等同把变量号当数组下标用。
   不实现这个，战斗系统会静默出错（不崩溃，但数值全错）。

5. **`parseCondition` 抛异常而非返回 null**
   `"% zukanon=2"`（前导空格产生空 token）会让 `?` 走进变量分支并抛
   `ParseException`，异常冒泡后整个 `if` 被判定为无法解析——
   掩盖了 `%zukanon=2` 本可解析的事实。

#### 最终解析结果（真实数据）

```
instructions : 441,712
labels       : 9,771
defsubs      : 18
numalias     : 1,200
by kind      : EMPTY=42,716  COMMAND=287,753  LABEL=9,771  TEXT=101,472
UNKNOWN 指令 : 0
parser 问题  : 6（均为原文笔误）
```

### 4.3 指令语义的关键修正

参考文档核对后修正的语义（这些写错不会崩，但会静默画错/算错）：

| 项 | 错误做法 | 正确做法 |
|---|---|---|
| `lsp2` 坐标 | 左上角 | **图片中心** |
| 精灵 Z 序 | 号大靠前 | **号小靠前** |
| 旋转方向 | 顺时针 | **逆时针为正** |
| `print 10,3000` | 翻页等待 | **10 号特效持续 3000ms** |
| `msp2` 不透明度 | 绝对值 | **增量**（基准 255） |
| `return *label` | 忽略参数 | **返回并跳转**（1,672 处） |
| `defsub` 分派顺序 | 先查内建 | **先查 defsub**，行首 `_` 才绕过 |

### 4.4 已知的安卓阻断项（诚实披露）

**3 参 `print` 会调用 x86 Win32 DLL**，共 288 处：

```
breakup.dll/urb   (171)
lngtwave.dll/vwi   (73)
breakup.dll/lrB    (32)
trvswave.dll/h     (11)
NSFont.dll          (1)
```

这些是 x86 原生 DLL，**Android 无法加载**，必须用 Kotlin 重写同等特效
（画面碎裂、水波纹、字形变换）。目前这些调用会被记为未实现并跳过
（不会崩，但特效缺失）。

另有 19 处 `mpegplay` / 1 处 `avi`（视频播放）同样需要原生替代。

## 5. 阶段五：构建环境

### 5.1 拉取工具链（实测耗时）

| 组件 | 大小 | 耗时 |
|---|---|---|
| Gradle 8.7 | 128 MB | 140 s |
| cmdline-tools | 146.5 MB | 699 s |
| platform android-34 + build-tools | — | 数分钟 |

### 5.2 踩到的构建坑

1. **`jvmToolchain(17)` 失败**
   机器上只有 JDK 21，Gradle 找不到 JDK 17 工具链。
   → 改为直接用 JDK 21 编译，`jvmTarget` 仍设 17，
   并在 `gradle.properties` 固定 `org.gradle.java.home`。

2. **Android 插件拒绝中文路径**
   ```
   Your project path contains non-ASCII characters.
   ```
   项目路径 `D:\开源项目\06-游戏移植\...` 含中文。
   → 加 `android.overridePathCheck=true`。
   **这是真实存在的 Windows 兼容性问题。**

3. **`application.mainClass` 写错**
   `main` 在 Kotlin `object` 里，生成的类名是 `Main` 而不是 `MainKt`。

4. **参考文档子代理留下的 GPL 源码镜像**
   `docs/ref/_src/` 有 2.87 MB 的 ONScripter GPL 源码片段。
   本仓库是 MIT。**已删除**，否则许可证冲突。

## 7. 复盘：本次任务的五个判断

### 判断 1：先勘察，再动手

需求字面是「转成安卓版」。如果不先勘察，会一头扎进「反编译 exe」这种不存在的路线。
**1.1 MB 的 exe 暴露了「这是解释器」这个决定性事实。**

### 判断 2：用实测推翻既有结论

旧项目已经写了 6 篇文档论证「必须用 Winlator」，
但它基于一个**未经验证的假设**——`nslua.dll` 被使用了。
实测脚本里 Lua 引用为 **0**，结论直接反转。

> **别人写得很详细，不等于它是对的。关键假设必须自己验。**

### 判断 3：把「可验证性」当作架构目标

把引擎核心做成零 Android 依赖，不是为了好看，
而是**唯一能对 380k 行真实脚本做回归测试的方式**。

### 判断 4：在字节层面反复出错时，换工具而不是继续推理

`.nsa` 格式我错了至少 5 次，每次都以为这次对了。
真正解决问题的是**写脚本把原始十进制值全打出来**，以及
**穷举候选布局让数据自己选**。
手工推演在遇到字节序、对齐、变长字段时就是不可靠的。

### 判断 5：及时止损，并把取舍写清楚

`.nsa` 索引格式花了过多时间。最终选择签名扫描，
并**在代码注释和文档里明确写出这个取舍的代价**（数据精确、文件名尽力），
而不是假装它完美解析了。

> 不是所有技术问题都值得解决，但**每一个没解决的都必须说清楚**。
